# Team Member 缓存命中率：三 Agent 下一阶段优化执行计划

> 状态：待执行，日期：2026-09-24。
> 本计划基于 `TEAM_MEMBER_CACHE_ROOTCAUSE_EXPERIMENTS.md`、前序 Part A/Part B 交叉审查结论摘要，以及现有审计和 benchmark 结果制定。交叉审查原文件已从工作区移除；下文保留其关键证据边界，不把历史相关性写成已证实根因。
> 主线拆为三个 Agent 并行执行：Agent A 负责数据可信度，Agent B 负责真实 Provider 实验，Agent C 负责候选优化、质量护栏与最终准入。

## 1. 当前结论与优化原则

### 1.1 当前结论

现有材料只支持以下有限判断：

- 所选 2026-09-24 早间路由样本低于所选 2026-09-23 样本，但样本按账本行数截取，并非等长时间窗、同任务组成或有效独立请求；只能作为待复核历史信号，不能直接称为稳定日间下降或生产基线。
- Part A 的 12 条真实 Team 记录可以初步验证观测链路和成员隔离，但样本不足以代表生产总体，也不能作为成员平均命中率基线。
- 同尺寸桶仍存在差异，只能削弱“纯 prompt 尺寸组成变化”的解释；任务内容、会话阶段、工具输出、成员和路由组成差异仍未排除，不能据此排除 P5。
- 将账本相邻行的 prompt 差解释为“每轮新增内容”证据不足：缺少可靠 session/request identity，聚合行也不能还原真实 attempts；因此不能据此排除 P2。
- 离线 benchmark 只验证特定 mock 和特定消息构造下的 append-only 行为；不能证明真实 Provider 的缓存键、TTL、scope、容量或命中行为，也未覆盖所有生产路径。
- `hit == 0` 只能表示“该记录未报告 cache read”，不能直接称为冷启动。Provider scope、容量、账号池和 usage 语义仍是待验证因素。
- D1“前缀中段被重写”和 D2“Provider 侧 scope/容量变化”均为候选解释，不是已证实根因。简单 TTL 无阶跃也不能排除其他 Provider 侧因素。
- Part A 的 `+4.00pp` / `+5.52pp` 模型数字依赖未验证代理变量，不得作为预期收益、验收目标或优化承诺。

### 1.2 优化原则

1. 先修正数据和推断边界，再做行为优化；不因为命中率下降就改变分母、排除低命中样本或重分类 usage。
2. 历史无身份账本只能用于路由级探索，不能补造 session 链、warm/cold 标签或每轮新增量。
3. 真实 Provider usage、实际请求字节和 route/model 稳定性是因果实验的最低条件；本地 hash、账本闭合关系和离线 mock 不能替代它们。
4. 一次只改变一个因素；任何生产请求行为改动都必须有开关、回滚和任务质量护栏。
5. 优化成功不只看命中率，还要同时看任务质量、必要上下文保留、延迟、输入 token、成本、工具可用性和观测覆盖率。
6. 证据不足、实验不可复现或 Provider usage 不可解释时，合格结论是“不改/继续采样”，不是强行提交代码。

## 2. 三 Agent 并行分工

### Agent A：数据可信度、成员级观测与统计契约

**目标：**成为数据基础设施和统计口径的唯一所有者，回答每条记录代表哪个成员的哪次请求、usage 从哪里来、能否纳入主指标，以及哪些内容仍不可验证。

**职责：**

- 核验 Provider usage 到 Team member owner writer 的完整数据流，确认成员归属、写入者、usage 来源和字段变换。
- 冻结唯一统计契约：观测单位、主指标、分母、排除项、prompt 分桶和各类平均值。
- 区分“未报告 cache read”“无 cache split”“unknown/estimated”“invalid accounting”和真实可纳入样本；不得把它们默认为 0 hit 或冷启动。
- 核实 session、逻辑 turn/request、Provider request、Provider attempt 的关联语义；只有实现确实保证身份时，才用于会话级分析。
- 核验脱敏、保留、写入失败和损坏恢复语义；观测故障不能阻断成员执行。
- 产出可复跑的成员级覆盖率、数据质量和分层基线报告，不对缓存根因做因果宣称。

**输入：**

- `TEAM_MEMBER_CACHE_OBSERVABILITY_PLAN.md`、`TEAM_MEMBER_CACHE_DATA_AUDIT.md`。
- 当前 provider usage 归一化、usage 聚合、Team owner writer、cache report 和测试实现。
- 前序审查限制：不能从相邻账本行推断同 session 增量，离线 mock 不能证明 Provider 行为。

**交付物：**

1. 字段实现核验清单：来源、写入点、转换规则、是否为原始 Provider 值、可否用于比较。
2. 冻结版统计契约，至少定义 session/逻辑请求/attempt ID、有效单请求条件、主指标和排除分类。
3. 成员隔离、重试/attempt、聚合识别、缺字段、usage 类型、日志失败和敏感正文不落盘测试。
4. 可复跑数据质量报告：总样本、有效样本、排除明细、字段覆盖率、成员及 route/model 分层、不可支持的结论。
5. 提供给 B/C 的契约版本、复跑入口、限制清单和变更通知机制。

**验收标准：**

- 每个纳入主指标的样本都有明确成员、usage 来源、统计单位和纳入理由。
- `request_count` 缺失或默认补成 1 时，不自动认定为单请求；单请求资格必须可审计。
- 低命中样本不因结果不利而过滤；有效、排除和未知样本均计数。
- 同一输入和筛选条件可确定性复跑，并能与原始记录对账。
- 观测日志不含 prompt、工具参数/结果正文或 secret；日志故障不阻断成员请求。
- `hit == 0` 统一表述为“未报告 cache read”；本地 prefix hash 只用于客户端差分，不称为 Provider cache key。

**禁止事项：**不改 provider-visible 请求字节、缓存策略、上下文裁剪/折叠策略或成员隔离；不根据账本相邻行补造 session/request 关联；不把 `prompt == hit + miss` 当作 Provider usage 正确性的独立证明。

### Agent B：真实 Provider 固定请求受控实验

**目标：**在固定请求字节、固定 member、固定账号范围和固定 route/model 下，确认真实 Provider 是否稳定报告 cache read，并识别间隔或某个明确客户端差异是否与结果相关。

**职责：**

- 选择无敏感、可重复、结果可校验的合成任务；固定 member、Provider、凭证/账号范围、model、route、请求参数、工具面、客户端版本和并发设置。
- 逐次记录实际请求哈希/长度、实验配置、版本、时间、原始或可追溯 usage、响应状态和任务质量结果；不落 prompt 或工具正文。
- 区分首请求、warm 请求、usage 缺失/无效、错误、重试和聚合结果；不得将它们静默当成 0 hit 或冷启动。
- 只对实际受控变量做解释；无法控制的 Provider 状态、并发、路由漂移或账号池变化必须作为混杂因素报告。
- 不提交生产缓存行为变更；若结果指向客户端因素，只向 Agent C 提供证据和候选建议。

**实验矩阵：**

| 阶段 | 固定条件与单一变量 | 目的与边界 |
|---|---|---|
| B0 Pilot | 固定字节、route/model、账号范围；每条件至少 8 次 | 检查 usage 可用性、请求稳定性、错误率和方差；不作收益结论 |
| B1 基线重复 | 完全相同字节、同 route、串行短间隔；首请求与 warm 分开 | 建立真实 Provider 报告基线；字节或 route 漂移的样本不得入基线 |
| B2 间隔对照 | 只改变请求间隔，其他条件不变；交叉/分块执行 | 观察间隔相关性；无重复阶跃只能说未观察到简单间隔效应 |
| B3 单组件扰动 | 只改变一个消息/工具 schema/序列化组件，再恢复基线 | 测量该具体差异与 usage 的关系，不泛化到其他组件 |
| B4 长上下文阶梯 | 预先冻结短、中、长合成请求字节，分别重复 | 观察规模分层行为；不同尺寸差异不能直接当作长度因果 |
| B5 route/账号探索 | 仅在配置获准且可明确控制时改变 route 或账号范围 | 观察配置相关性；不能单独证明 scope、容量或 Provider 根因 |
| B6 版本对拍 | 同机同夹具对比指定客户端构建 | 仅在请求差分和 usage 都可追溯时评估版本关联，不据此自动回滚 |

**样本与停止规则：**

- Pilot 每条件至少 8 次；据 pilot 在正式运行前登记样本量、最小关注效应、费用上限和停止条件。
- 正式实验建议每臂至少 30 个有效 warm requests，最低不得少于 20 个；首请求单列。有效样本必须满足请求字节、配置、route/model 和精确 usage split 均可确认。
- 达到预注册样本量即停止；若需提高检验力，必须在查看正式结果前登记，建议上限为每臂 100 个有效 warm requests。
- 仅因费用上限、连续服务错误、usage 不可用、路由漂移、输入字节失控、敏感内容或任务质量/安全问题停止；不得因中途命中率有利或不利而提前结束。
- 同时报告 token 加权率、hit/miss tokens/request、请求级分布、绝对百分点差异、配对区间、错误率、延迟、输入 token 和费用。

**验收标准：**另一成员可按文档重放；每条样本可关联配置、输入摘要、版本、usage 来源和质量结果；pilot/正式数据分开；所有偏离、排除和无效样本公开；结论只覆盖真实受控条件，允许结论为“未决/不建议改代码”。

**禁止事项：**不以本地 prefix hash、离线 mock 或历史相邻账本行补足真实 Provider 证据；不同时切换 model、route、任务和缓存配置；不因结果不理想删样本。

### Agent C：候选优化、独立复核、质量护栏与灰度

**目标：**独立复核 A/B 的证据强度，将通过证据门的单一因素转为最小候选改动，并负责质量、成本、灰度、回滚和最终合流。Agent C 不能为了完成任务而强行产生生产代码。

**并行阶段职责：**

- 对 A 的字段契约、基线和报告做独立复核，不另立统计口径；检查历史结论是否超出证据。
- 对 B 的实验夹具、变量控制、样本量、usage 追溯和结论措辞做独立复核。
- 静态审查请求构造、工具 schema、工具输出、fold/compaction 和版本差异，建立候选清单；此阶段不改 provider-visible 行为。
- 为每个候选准备质量/成本测试、feature flag、回滚步骤和灰度观测字段。

**候选优化顺序（条件排序，不是预设根因）：**

1. 修正被请求差分和真实 Provider 对照共同支持的稳定前缀意外变化。
2. 若固定工具 schema 尾部成本被实验支持，再评估有界剪枝或描述优化；确保工具可达性和成员权限不变。
3. 若工具输出或重复状态被实验支持，再评估限量、摘要或分段读取；不得丢弃任务所需信息。
4. 若低命中明确集中在 fold/compaction 边界且对照确认收益，再调整摘要插入位置或 fold 策略。
5. Provider scope、TTL、容量或路由亲和性先作为待确认事项，不用猜测性客户端改造绕过。

**决策门：**

- **C0 接口冻结：**A/B/C 对有效请求、主指标、排除项、usage 精度、版本和实验变量达成一致。
- **C1 证据准入：**A 的成员归属和诊断覆盖率可用；B 提供真实 Provider、单变量、可重复的对照结果；历史无身份线索不能单独放行。
- **C2 候选准入：**候选只处理一个被支持因素，有基线差分、预注册判定、质量/成本测试和快速回退路径。
- **C3 灰度准入：**合成/回放测试通过后，限单一测试 member，再进入小比例白名单；按有效样本数判断，不以时间代替样本量。
- **C4 扩大、回滚或停止：**命中改善超过 pilot 噪声范围且重复方向一致，同时质量不劣、延迟/成本/错误率和观测覆盖率不越界；任一硬护栏触发即关闭开关。
- **C5 最终合流：**三方复核指标口径、实现范围、回归结果、灰度结论和残余不确定性，决定合并、扩大、回滚或“不改”。

**交付物：**候选变更登记表、独立复核意见、最小补丁或“不实施”决定、开关/回滚步骤、质量成本护栏清单、灰度记录和最终合流报告。

**禁止事项：**不把离线 mock 或历史相邻账本作为改动依据；不修改统计分母；不通过破坏成员隔离、删减必要上下文或过滤低命中样本获得表面收益；未通过 C1 前不改生产请求构造。

## 3. 三 Agent 交接接口

| 接口 | Agent A 提供 | Agent B 提供 | Agent C 消费/产出 |
|---|---|---|---|
| 数据口径 | 契约版本、有效样本规则、usage 语义、排除分类、复跑入口 | 按契约记录实验样本和无效样本 | 独立复核，不另立分母；输出 go/no-go |
| 请求证据 | 成员/逻辑请求/attempt 关联及脱敏诊断能力 | 固定请求哈希/长度、route/model、版本和 Provider usage | 验证候选是否只改变目标组件 |
| 实验结果 | 覆盖率、成员归属、基线分层 | 真实 Provider 重复实验、效果波动、混杂因素、质量结果 | 转换为候选、质量测试和灰度方案 |
| 行为代码 | 观测、契约和报表实现 | 实验夹具和结果，不改生产行为 | 仅在 C1 后提交最小生产改动 |

三方不得并行修改同一统计契约或同一生产请求构造文件。若 A 的契约发生变化，B 必须标记实验版本，C 必须重新确认结论是否仍可比较。

## 4. 里程碑与合流门槛

| 阶段 | Agent A | Agent B | Agent C | 合流门槛 |
|---|---|---|---|---|
| **M0 契约冻结** | 发布统计/隐私/关联契约草案 | 审阅实验所需字段 | 审阅证据等级和质量护栏 | 三方确认分母、usage 精度、变量和文件边界 |
| **M1 链路与夹具** | 核实现有 owner writer、成员隔离和字段缺口 | 构造固定任务与重放夹具 | 独立复核历史报告和候选风险 | 能追溯请求形状与 usage；不足则不进入因果实验 |
| **M2 Pilot** | 发布覆盖率和数据质量报告 | 执行每条件至少 8 次 pilot | 复核方差、偏离和样本量 | 预先冻结正式样本量、效应阈值和停止规则 |
| **M3 根因判定** | 固化可比基线和排除项 | 完成单变量真实 Provider 对照 | 出具 C1/C2 准入意见 | 只能对证据支持的单一因素提出改动 |
| **M4 灰度验收** | 监测口径和覆盖率不变 | 提供对照与质量结果 | 实施最小补丁、灰度、回滚和最终合流 | 达到 C3/C4 才扩大，否则回滚或“不改” |

## 5. 最终报告模板

- **范围：**代码版本、Provider/model/route、成员范围、任务类型和时间窗。
- **样本：**总请求、有效单请求、warm/首请求、聚合/unknown/estimated/error 数及排除原因。
- **指标：**`Σhit/(Σhit+Σmiss)`、hit/miss tokens、请求级分布、prompt 桶、会话阶段和间隔分层。
- **请求差分：**组件类别、长度/token 数、hash/首个变化边界；不附正文，不将本地 hash 当 Provider key。
- **实验：**条件、顺序、次数、方差/区间、usage 来源、并发/重试和其他混杂因素。
- **护栏：**任务正确性/质量、延迟、输入 token、成本、工具调用、错误率和 telemetry 覆盖率。
- **结论：**支持/反对/未决假设、证据等级、适用范围及无法排除项。
- **决策：**不改、继续采样、实施哪项最小优化或回滚；附负责人、开关和复查日期。

## 6. 近期执行顺序

1. Agent A 先盘点现有 recorder、`.cache_requests.jsonl`、owner writer、成员隔离和 usage 字段；把 12 条 Team 记录定位为链路 smoke test，不作总体基线。
2. Agent B 同时准备无敏感固定任务、请求字节校验、route/model 固定方式和 Provider usage 可用性检查；离线 benchmark 仅作为夹具自测。
3. Agent C 同时复核现有报告措辞，标记“每轮新增内容”、P2/P5 排除、D1/D2 根因和 cold/warm 术语的证据等级，并建立候选变更登记表。
4. M0 通过后，A 做最小脱敏观测补缺，B 执行 pilot，C 独立复算和检查；三方不改变 provider-visible 请求行为。
5. Pilot 结束后，在正式数据开始前冻结样本量、最小关注效应、非劣标准、费用上限和停止规则；历史相邻账本行不进入会话级实验统计。
6. B 完成真实 Provider 对照后，A 复核数据覆盖和统计口径，C 出具 C1/C2 准入意见；若 usage 不可信、route 不可控或结果不可复现，结论为“未决/继续观测”。
7. 只有通过决策门的候选才由 C 实施最小补丁、回归、白名单灰度和回滚；扩大范围前同步更新命中、质量、延迟、成本和 telemetry 报告。

## 7. 完成定义

- 能区分路由级历史线索与成员级可比基线，且不把 12 条样本或账本相邻行当作总体/会话证据。
- 能解释每个纳入样本的成员归属、请求单位、usage 来源和排除理由。
- 能在真实 Provider 上重放固定请求，并区分首请求、warm 请求、usage 缺失和错误。
- 能将客户端请求差异、工作负载混杂和 Provider 待确认因素分开报告。
- 任何生产行为优化都有真实 Provider 对照、任务质量护栏、开关、回滚和灰度证据。
- 若缺少可追溯 usage、稳定 route 或足量成员级数据，最终结论明确停留在“线索/未决”，不得宣称已找到根因或已完成命中优化。

## 8. 并行派单摘要与依赖管理

以下任务可直接派给三个 Agent。M0 契约冻结是共同约束，但不必等所有分析结束后才启动：A、B、C 可先分别做只读盘点，正式采集或改动前再合流确认契约。

### 派给 Agent A：数据链路与成员基线

> 核验 Team member 缓存 usage 从 Provider 返回到 owner writer、`.cache_requests.jsonl` 和报表的完整数据流。先复用现有实现，不预设新增遥测。输出字段来源/转换表、统计单位与有效样本规则、成员隔离与记录覆盖率、历史数据不可验证项及可复跑基线。重点确认 `request_count` 缺失/默认值、聚合/重试/attempt、usage 精确/估算/未知和 cache split 缺失语义。补充最小必要测试，但不要修改 provider-visible 请求或缓存行为。旧账本相邻行不得当作同一 session；12 条样本只作为链路 smoke test。交付契约版本和对 B/C 的字段接口。

### 派给 Agent B：真实 Provider 实验

> 准备并执行固定合成输入的真实 Provider 重复实验。固定 member、账号范围、route/model、客户端版本和并发；逐请求记录请求哈希/长度、配置、usage 原始来源、响应状态、延迟与任务正确性，不保存 prompt/工具正文。先跑每条件至少 8 次 pilot，再预注册正式样本量、效应阈值、费用上限和停止规则；正式样本建议每臂至少 30 个有效 warm requests。按基线重复、间隔单变量、单组件扰动、长上下文阶梯顺序开展。无法确认 usage、请求字节或 route 时停止因果判读并报告未决；不要修改生产行为或统计口径。

### 派给 Agent C：独立复核与优化准入

> 独立复核历史报告与 A/B 输出，不另立统计口径。先标注账本抽样偏差、相邻行伪会话推断、P2/P5“排除”、D1/D2 根因、mock 外推和 `hit == 0` 冷启动等措辞风险；复算结果时记录所用契约版本。并行建立候选优化登记表，按“证据—目标请求组件—预期收益—质量/成本风险—反证条件—回滚方式”描述候选，并准备质量/成本回归及灰度计划。A/B 证据门未通过前只做只读审查和方案，不改生产请求；最终给出 go/no-go 或“不改/继续采样”。

### 并行与依赖图

- **可立即并行：**A 只读盘点 recorder/报表；B 验证 Provider usage 和固定 route 的可行性；C 复核历史结论、审阅 benchmark 边界并准备候选登记表。
- **需先合流：**正式实验开始前冻结 usage 语义、纳入/排除条件、请求差分记录格式、隐私边界、实验版本及停止规则。
- **依赖关系：**A 的字段契约供 B 标记实验数据、供 C 独立复算；B 的真实 Provider 结果与 A 的可信基线共同决定 C 是否能进入行为改动；C 的实施不能反过来改变 A 的统计定义或 B 的实验变量。
- **代码冲突隔离：**A 独占观测/统计契约及报表文件；B 独占实验夹具和实验记录；C 在准入前只提交候选设计，准入后如需修改生产请求代码，先与 A/B 确认接口和冻结对照版本，不与其并行改同一文件。

### Provider 实验不可行时的分支

如果无法获得可追溯的 Provider cache usage、无法稳定固定 route/account，或真实实验费用/安全边界不允许：

1. B 交付不可行性证据、缺少的 Provider 能力和最小外部依赖，不用 mock 代替结论。
2. A 继续改善成员级观测与可比基线，但明确这些数据只能支持描述性分析。
3. C 不放行生产缓存行为变更；可提出本地请求稳定性修复候选，但须将其效果标为“未验证 Provider 命中收益”，不能以缓存优化名义灰度。
4. 联合结论记为“因果验证受限/暂不改行为”，列明恢复实验所需条件与复查触发点。
