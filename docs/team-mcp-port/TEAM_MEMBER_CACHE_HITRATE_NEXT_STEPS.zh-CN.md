# Team Member 缓存命中率：下一步执行方案（Part A / Part B）

> 状态：执行方案。目标是验证 2026-09-24 早间账本异常并定位可行动根因；不预设命中率下降由代码、工具 schema 或上下文长度单独造成。
> 前置分析：`docs/team-mcp-port/TEAM_MEMBER_CACHE_HITRATE_ANALYSIS.md`。
> 分工：Part A 与 Part B 可并行；两部分先共同冻结统计契约，最终由集成负责人合并结论。

## 1. 目标与原则

最终回答以下问题，并为每个答案标明证据、推断或未决：

1. 命中率变化是否真实、持续，且发生在具体哪些 member、route、prompt 桶和请求阶段？
2. 低命中主要与稳定前缀变化、请求内容新增、请求间隔/缓存生命周期，还是数据质量/聚合口径相关？
3. 哪个可控改动在受控对照下确实改善缓存命中，且没有损害任务质量、延迟或 token 成本？

执行原则：

- 账本 `prompt == hit + miss` 只代表记录满足本地字段关系；若该关系由 provider adapter 归一化，不视为独立验证 provider 原始数据。
- 先按 provider request 统计；聚合 usage（`request_count != 1`）、unknown、estimated、账目无效和 cache split 缺失分别列出，不冒充单请求样本。
- 用相同时间窗、route/model、member、prompt 桶和请求阶段做比较；路由级历史账本不得称作 Team member 级结果。
- 本地 prefix hash/reasons 是诊断线索，不是 provider cache key 或 miss 因果的证明。
- 先观察和实验，再改行为；优化不得通过减少记录、改变分母或排除低命中样本来“提升”指标。

## 2. 并行工作包与接口

| 工作包 | 责任 | 主要交付 | 可并行边界 |
|---|---|---|---|
| **Part A：数据与基线审计** | Agent A | 数据质量审计、可比基线、成员级分层报表、异常请求清单 | 独立核实事件/记录的请求单位、筛选条件和报表输出；不改缓存行为 |
| **Part B：根因实验与候选改进** | Agent B | 预注册实验矩阵、实验结果、经过验证的改进 PR 或“不改”的证据 | 先基于已存在字段设计实验；行为改动须等 Part A 冻结口径后评估 |

两部分共用的统计契约：

- 主指标：精确、有效、单 provider request 的 `Σcache_hit / (Σcache_hit + Σcache_miss)`；同时报告 hit/miss token 总量和有效样本覆盖率。
- 伴随指标：请求命中率中位数/P10/P90、`prompt_tokens`、miss tokens/request、任务成功率、工具调用结果质量、延迟及输入成本。
- 分层字段：member、provider/model/route、请求时间窗、`context_prompt_tokens` 桶、请求阶段、距上一请求间隔、`request_count`、usage 精确/估算/未知、prefix diagnostics。
- Prompt 桶采用现有固定边界：`<32k`、`32k–128k`、`128k–256k`、`256k–512k`、`512k–768k`、`768k–1m`、`>=1m`。`context_used` 只作旁证，不作 prompt 桶键。
- 输出必须包含查询时间窗、代码版本、样本数、member 数、有效/排除/未知数量及排除原因。无样本或样本不足须显示 N/A/低置信度。

## 3. Part A：数据质量与可比基线

### A1. 复核 usage 语义与统计单位

1. 梳理 `provider.Usage`、重试/采样合并、stats recorder 和 Team request recorder 的数据流，列出原始 provider usage、归一化值和落盘字段的关系。
2. 用 fixture 或测试证明 `request_count`、`context_prompt_tokens`、`usage_unknown`、`usage_estimated`、`accounting_valid` 的语义；确认多 request 聚合不能被当作多个独立请求样本。
3. 检查 DeepSeek 适配层是否对原始 `input_tokens`、cache read/write 字段做了归一化。若账本不保留原始字段，则明确标注该历史账本不能独立排除上游统计口径问题。
4. 区分“零 hit”“没有 cache split”“unknown/estimated”与“确认冷请求”；没有 session/request 身份时不得从 `hit == 0` 推断冷启动原因。

**交付 A1：**字段数据流表、有效样本规则、旧账本可验证/不可验证事项清单。

### A2. 生成同口径基线

1. 先复算历史数据，并提供等长窗口对比（至少包含 09-23 与 09-24 同一时段）；完整日期和部分日期单独标记，不直接称为日对日因果变化。
2. 对 `requests > 1` 聚合样本同时给出 token 加权总量和“排除聚合样本”的逐请求分布；若无法拆分成真实 attempts，则不按请求率分布展开。
3. 对现有 `.cache_requests.jsonl` 生成近期 Team member 级报告，确认记录确实来自 member owner writer，排除 leader/普通 CLI/follower 重复写入，并核实诊断覆盖率和记录保留边界。
4. 按 member、route/model、prompt 桶、request interval、prefix-change 状态和 usage 质量分层。历史路由级账本只作背景对照，不与新 member 级样本直接拼接。
5. 报告样本不平衡和时间/任务组成差异；至少展示各组请求数、prompt/miss 总量、加权率及置信区间或明确的低样本提示。

**交付 A2：**可复跑命令或报表文件、历史与近期基线、数据覆盖率/偏差说明、需要补采的数据清单。

### A3. Part A 验收

- 多 request 聚合、未知/估算、无效账目、零分母有独立计数，不静默修正或并入主基线。
- 报表的总 hit/miss 与选定原始记录一致；同一份输入和过滤条件可重复生成相同结果。
- 至少能分辨具体 member/route/prompt 桶；没有维度数据时明确显示未知，而不是推断归属。
- 输出一份数据审计结论：当前下降是否在可比样本中复现，以及证据覆盖哪些时间和成员。

## 4. Part B：根因区分与受控实验

### B1. 预注册假设与判别信号

Part B 在看实验结果前记录假设、对照、指标及停止规则，至少覆盖：

| 假设 | 可观察信号 | 不能单独作为证明的信号 |
|---|---|---|
| P1：provider-visible 稳定前缀发生变化 | 同一 member/route 的相邻请求 prefix hash 或可追溯前缀字段变化；变化后 miss 有可重复增量 | `stable_prefix_changed=true` 本身不能证明 provider 因此 miss |
| P2：请求新增内容/工具结果变大 | 同一稳定前缀下 prompt/miss 增长，并与本轮新增内容/工具输出 token 量相关 | 单纯 `stable_prefix_changed=false` 不能证明其余内容是唯一变化 |
| P3：请求间隔或缓存生命周期影响 | 固定任务/前缀条件下，命中随请求间隔或缓存 TTL 条件呈可重复变化 | 将零 hit 直接称为冷启动 |
| P4：usage 口径或聚合造成表观变化 | 异常集中于特定 usage source、聚合 attempt、缺失/估算或 adapter 口径 | `prompt == hit + miss` 单项闭合检查 |
| P5：模型/route/任务组成变化 | 变化集中于 route/model/member/工作负载构成，分层后总体差异明显减弱 | 不分层总体日均命中率 |

### B2. 实验设计

1. **历史观察分析：**使用 Part A 验收后的记录，先检查 P4/P5；再分析 prefix 变化、请求间隔、prompt 增量与 miss 的相关性。此阶段只提出候选根因，不宣称因果。
2. **可重复基准任务：**选择固定输入、固定 member/route/model、固定工具集合的代表性任务；覆盖中短上下文及至少一个长上下文负载。对同一任务重复运行，记录任务成功/质量、实际 prompt/cache split、响应延迟和工具输出规模。
3. **单变量对照：**每次只改变一个因素，例如稳定前缀内容/顺序、可变上下文位置、工具 schema 或工具输出体积。不得同时切换模型、route、任务和缓存相关配置。
4. **配对/交叉运行：**按相同任务成对运行候选组和基线组，平衡先后顺序；尽量使用相同 route 与相近请求间隔。记录无法控制的缓存 TTL、并发请求和 provider 侧状态，作为混杂因素报告。
5. **重复与样本量：**先做小规模 pilot 估算波动，再预先确定每个条件的运行次数和最小可检测效果；未达到计划样本量不得用单次高命中结果作为结论。
6. **候选优化优先级：**只针对实验支持的因素提出最小改动。优先检查稳定前缀是否有无意义变化、长工具结果是否可有损/可逆压缩，以及请求阶段是否重复引入不稳定内容；不因提交时间相邻就直接回滚工具/skill 改动。

**安全约束：**实验记录不得包含 prompt 正文、工具参数/结果正文或 secret；如需分析内容增量，只保存经批准的 token 数、类别、短 hash 或脱敏标签。对真实用户任务不做破坏性清理或隐式模型/路由切换。

### B3. 优化验证与灰度

仅在某个因素通过配对实验显示可重复改善后，才实现对应行为改动。改动必须提供开关或可快速回滚路径，并按 Team/member 白名单灰度。

接受改动需同时满足：

- 主命中指标改善超过 pilot 确定的噪声范围，且跨重复运行方向一致；同时报告绝对 pp 变化及 miss tokens/request 变化。
- 任务成功率/质量不劣于预设容忍范围；长上下文任务不能以遗漏必要上下文换取命中率。
- 延迟、总输入 token、成本及工具调用次数无不可接受回退。
- 改动前后 route、模型、样本筛选、usage source 和统计口径一致；所有排除项公开。
- 灰度期间持续采集逐请求记录；命中率无效、任务质量下降或统计覆盖率异常时自动/人工关闭开关并保留诊断数据。

若候选优化未通过以上标准，Part B 的合格交付可以是“不应实施该改动”，并附实验条件、负结果和不确定性。

## 5. 里程碑、依赖与合流

| 阶段 | Part A | Part B | 合流门槛 |
|---|---|---|---|
| M0：契约冻结 | 核实字段与样本规则 | 登记假设、候选因素与停止规则 | 双方使用相同主指标、筛选条件和排除规则 |
| M1：并行分析 | 历史重算、member 数据覆盖审计 | 设计基准任务和配对实验，不动行为代码 | Part A 确认哪些数据可比较；Part B 的实验方案可复现 |
| M2：基线通过 | 发布同时间窗/分层基线 | 运行 pilot，估算方差和样本量 | pilot 数据符合 A 的有效 usage 规则 |
| M3：验证与实现 | 固化基线报表和质量报告 | 执行正式实验；仅对通过项实现最小改动 | 有原始聚合数据、重复结果和质量/成本对照 |
| M4：灰度验收 | 监测报表覆盖与分层指标 | 白名单灰度、回滚或扩大范围 | 达到 B3 验收；否则回滚并记录结论 |

建议文件边界：Part A 主要改数据审计脚本/报表与相关测试；Part B 主要改基准任务、实验配置及被证明必要的运行行为。两方避免同时修改同一统计契约或同一实现文件；需要跨层字段时先经 M0 评审。

## 6. 最终交付与决策模板

最终报告逐项填写：

- **观察到的变化：**时间窗、member/route、prompt 桶、有效请求数、加权命中率、miss tokens/request、覆盖率。
- **数据可信度：**usage source、聚合请求比例、未知/估算比例、原始字段是否可独立核验。
- **根因判断：**支持/反对 P1–P5 的信号、混杂因素、仍未排除的解释；不以 prefix hash 单独宣称因果。
- **实验结论：**对照条件、运行次数、效果量/波动、任务质量、延迟、成本及失败案例。
- **决策：**不改、继续采样、实施最小修复或回滚；写明负责人、开关、灰度范围和复查时间。

整体完成标准：能复现异常或明确说明不可复现；能区分数据问题与工作负载差异；对任何行为优化都有对照证据和任务质量护栏。若缺少成员级或 provider 原始 usage 数据，应把结论停留在“线索/待验证”，不得宣称已找到缓存命中率下降的根因。
