## 1. 当前状态与问题定义

上轮 A/B/C 的代码核验、观测链路复核和一次条件矩阵执行已完成，最终结论为 `NO-GO / CONTINUE-SAMPLING`。该结论表示评估工作有产物，但**主线优化效果没有得到验证**。

本轮只聚焦解除下列关键阻塞：

1. **A/B 行为路径未触发**：上轮最大 prompt 约 23.2 万 token，低于约 80 万 token 的维护触发线；计数为零不能证明有效或无缺陷。
2. **质量、完成率、延迟缺少可用观测**：当前记录无法回答压缩后任务是否完成、必要上下文是否保留、工具调用是否正确，以及端到端延迟是否回归。
3. **实验条件需要消除混杂**：Baseline/A-only/B-only/A+B 必须实际控制目标开关；既有 `cache_aware_compaction` 不应无意中与本轮 A 因子绑定。
4. **样本和环境范围不足**：每臂有效 warm 样本不足，桶级不足 30/3，单网关的 128 模型不能外推到其他账号、网关或并发条件。
5. **NO-GO 与默认开关需要明确对齐**：上轮记录两个开关默认开启，同时又要求不放行。执行前必须书面决定本轮如何处理默认开启行为及其部署范围；不得默认为 NO-GO 就等于开关关闭。
6. **A 因子必须完整可隔离**：逐项盘点 headroom 判据、low-yield latch、summary 抑制等哪些是真正改变运行行为的功能、哪些仅是 telemetry；不得只切换 latch 就声称 A-only 与 baseline 已隔离。

本轮成功标准不是“跑完脚本”，而是获得足以区分**优化未生效、优化无效、优化有效但有代价、证据仍不足**的可信数据。

## 2. 本轮范围与不变量

### 2.1 范围内

- 构造安全、可复现、可归因的维护路径触发实验；
- 冻结无混杂的条件矩阵、固定任务和样本有效性规则；
- 补充任务质量、必要上下文、工具调用、端到端延迟和成本观测；
- 复核 `append_block_allowance = 128` 模型的适用边界；
- 提供 go/no-go 证据和清晰回滚建议。

### 2.2 范围外

- 不直接扩大生产灰度或改变所有用户的行为；
- 不把降低 `compact_ratio` 的压力测试伪装成生产分布证据；
- 不把 128 视为 Provider 常量，不以 `provider_residual_unexplained == 0` 单独证明归因正确；
- 不改变 Provider usage 原始值、统计分母、任务脚本或样本剔除规则来制造改善；
- 不记录 prompt 正文、工具参数、凭据、原始答案或可还原用户内容；质量评测只存脱敏评分、规则命中和 artifact 标识；
- 不因测试绿、事件链路完整或路径计数非零就宣布行为优化有效。

## 3. 启动门禁与共享实验契约

### 3.1 协调者在并行启动前冻结

协调者须建立版本化的 `experiment-contract.yaml`（或等价记录），固定：

- 合流快照 commit 和内容哈希、Go 版本、构建标签；
- 实际部署/采样配置，以及 `low_yield_latch`、`message_shape_diagnosis` 当前默认值和显式值；
- `cache_aware_compaction` 的处置；
- A 侧所有行为性改动与纯观测改动的清单、各自开关及关闭时旧行为；
- 模型、route、账号作用域、网关、并发度、任务集、时间窗和请求预算；
- 下述四臂开关表、触发实验配置、有效样本定义、停止规则和分析方法；
- 质量评分 rubric、任务成功/失败定义、延迟计时边界；
- 原始数据保存位置、访问控制、保留期限及脱敏规则。

如果无法确认默认开启行为是否已经进入目标部署，**先做配置/发布状态盘点，不发起影响真实用户的采样**。

### 3.2 默认开启与 NO-GO 的冲突处理

协调者必须书面选择并记录以下其一：

- **方案甲：保留默认开。** 明确接受现存默认行为属于当前实际行为；实验结论不能表述为“尚未上线”，只允许限制进一步扩量，并确保有可执行配置回滚；或
- **方案乙：隔离未获准行为。** 通过显式部署配置关闭相关开关，或经审批调整默认/发布门禁；变更后验证实际消费配置与回滚路径。

没有这项书面裁定时标记 `BLOCKED`，不运行可能扩大真实行为暴露的 live 实验。不得由 Agent 自行改变默认值。

### 3.3 主矩阵：只测本轮两个可控因子

主矩阵采用 2×2，`cache_aware_compaction` 在所有臂固定为同一值（默认建议固定 `false`），避免将既有行为与新因子混为一谈：

| 臂 | `low_yield_latch` | `message_shape_diagnosis` | `cache_aware_compaction` | 解释 |
|---|---:|---:|---:|---|
| Baseline | false | false | 固定值 | 本轮对照 |
| A-only | A 侧全部已批准行为因子开启 | false | 同一固定值 | 只改变 A 因子 |
| B-only | false | true | 同一固定值 | 只改变 B 因子 |
| A+B | A 侧全部已批准行为因子开启 | true | 同一固定值 | 测 A 与 B 交互效果 |

Rescue 不属于常规矩阵，单独作为受控末端安全演练。若业务问题确实要评估 `cache_aware_compaction`，另开独立因子/矩阵，不得把它悄悄塞进 A-only。

### 3.4 样本与顺序规则

- 先 pilot，pilot 只用于确认装置、触发和方差，不并入正式效果估计。
- 正式实验每臂至少 30 个有效 warm request、覆盖至少 3 次独立运行；这是最低门槛，不保证统计功效。Agent C 必须在看正式结果前根据 pilot 方差冻结所需样本量、最小有意义差异和置信区间方法；若计算结果高于 30，以较高值为准。
- 固定任务采用配对或分层随机顺序，避免任务难度、时间、缓存冷暖、账号/route 漂移与实验臂绑定。
- 冷启动、warm、retry、错误、unknown、缺失 usage、Provider 聚合 attempt 分开统计；不允许把它们混为有效 warm 样本。
- 至少两个独立账号作用域和两个网关/route 才能作跨环境结论；`route_bucket` 不能当账号 ID。若本轮资源不允许，结果明确限于单账号/单网关，不作外推。
- 任何账号、网关或模型切换均记录为分层维度；超预算或触发安全停止阈值即停。

## Part A：真实维护路径触发与 A 因子验证

### A.1 目标

使维护状态机在可控环境中真实触发，证明每个实验臂确实消费了预期配置并观察到预期行为；区分压力测试的功能证据与真实使用分布上的效果证据。

### A.2 工作项

1. 盘点维护触发条件，给出可重复的两类任务：
   - **功能触发任务**：使用隔离测试账号/固定模型，在明确 token 预算下触发 fold、low-yield、headroom 和必要的 overflow 分支；
   - **生产代表性任务**：使用真实常见任务分布，不人为降低触发线，测量自然维护事件频率和效果。
2. 若用实验专用 `compact_ratio` 降低触发线：仅限隔离实验条件；将值作为显式实验变量写入 registry；记录其与生产阈值的差异。该测试只证明代码路径运行，不可用于生产收益结论。
3. 对 Baseline/A-only/B-only/A+B 每臂采集配置消费证据与维护事件：summary 请求数、projection install、状态结果、headroom、reduction ratio、latch block/release、rescue 次数、下一次相同 view 是否重入维护。
4. 验证超 hard ceiling、错误响应、重试、手动维护及中断恢复行为；安全边界优先于实验完整性，出现超限请求立即停止。
5. 对每次触发建立因果链：实验条件 → 成员实际配置 → 维护决策 → Provider attempt → usage/事件 → 后续 turn；事件为零时明确判为“未触发”。
6. 逐项区分 A 的行为变化与纯观测字段，确认 A-only 能隔离所有纳入评估的 A 行为；若 headroom 等行为变化没有独立 gate，应先提出最小 gate 方案，不得拿不完整 A-only 进入正式因果比较。复核各默认开关与关闭回滚在目标构建中可读、可消费、可恢复；不得自行修改默认值。
7. 汇总触发 prompt 分布、自然触发率、压力触发率及两者差别；提出生产代表性采样是否足够的判据。

### A.3 写集与协作界面

- 写集：A 专属核验报告、触发脚本/fixture 和 `internal/agent` A 侧定向测试；不得改 C 的统计管线或 B 的指纹算法。
- 生产行为代码若需改动，先交接口/差异提案给协调者批准；批准后仍由单一 Agent 负责共享文件。
- 对外接口：输出按样本记录的 `triggered`, `trigger_type`, `condition`, `maintenance_generation`, `same_view_repeat`, `headroom_tokens` 等最小字段；字段名以现有 schema 为准，不得并行创建重复真相源。

### A.4 交付与通过条件

交付 `PART_A_NEXT_RESULT.md`：触发配方、实际消费配置、原始脱敏日志、每臂触发统计、安全停止记录、测试结果和回滚步骤。

A 的通过条件：

- 至少一组真实触发的功能样本证明路径确实运行；
- 每臂配置消费值与冻结契约一致，Baseline 不含待测 A/B 因子，A 因子覆盖全部待测行为变化；
- 同一 view latch、headroom 和 hard ceiling 边界有证据；
- 压力触发与生产代表性证据分开报告；
- 无法自然触发不标为失败或成功，而标为“该生产路径尚未观测”。

## Part B：数据质量、任务质量/延迟观测与 128 外推边界

### B.1 目标

补齐“能否判断优化代价和质量”的数据契约，并把 128 模型限定在实际有证据的范围，避免报表字段产生错误账号/route 语义。

### B.2 工作项

1. 设计最小化的请求/turn 观测契约，至少包含：匿名实验样本 ID、条件臂、member/session lineage、账号作用域匿名 ID、网关/route/model、logical turn、attempt/retry、cold/warm、输入/缓存 token、维护/rewrite 原因、首 token/完成时间或明确定义的端到端 latency、完成状态和 unknown 原因。
2. 定义不记录答案正文的质量评估：
   - 每个固定任务预先指定可验证 rubric（必需事实/约束、工具调用目标、完成判据）；
   - 自动断言与盲评分开，评分者不知道条件臂；
   - 只保存评分项、错误类型、任务 ID 和必要的受控 artifact 引用，不保存敏感 prompt/答案；
   - 定义无法评分、评审分歧及安全失败的处理方式。
3. 延迟指标分清 provider 请求延迟、单 turn wall time、排队/重试时间；规定起止事件与时钟来源，按臂、模型、route 分层报告 p50/p90 和样本数。
4. 调查当前 `MemberCacheRequest`、`cachelab.Sample`、usage 发布链路能否承载字段；优先复用现有脱敏事件，新增字段需版本、owner、消费者和兼容策略，不复制多份维护事实。
5. 明确 `route_bucket` 是 route/pool entry 指纹，不是账号作用域；定义独立匿名 account-scope ID 的生成、轮换和访问规则，不记录凭据 hash 或原始 UserID。
6. 使用已有计算器重算 128 模型；规划至少两个账号作用域、两个网关/route、多个上下文桶的验证。报告每层 `n`、命中/违反、`max excess`、p50/p90/max、并发度和未知率；模型未跨环境通过前，仅称“在样本集内观察到的模型”。
7. 做 128 敏感性报告（现行 +128、较小阈值、零豁免、未知不归类），并解释不同规则如何改变 residual，禁止选择最有利口径作为主结论。
8. 制定隐私、安全与数据保留检查；任何会使数据可逆向恢复内容或凭据的方案不得实施。

### B.3 写集与协作界面

- 写集：B 专属 `PART_B_NEXT_RESULT.md`、数据字典、评分 rubric、分析脚本/离线样本；不得编辑维护状态机或正式实验 runner。
- 若需生产观测字段，先输出 schema 变更提案与消费者清单；由协调者指定唯一实现者，B 不与 C 同时修改 publisher/recorder。
- 输出给 C 的接口：冻结字段字典、样本有效性标签、latency 定义、质量评分格式、account-scope 语义和 128 重算工具。

### B.4 交付与通过条件

B 的通过条件：

- 质量和延迟指标具有明确可复现定义，且不采集敏感正文；
- account scope 与 route identity 分离，不以 `route_bucket` 代替账号；
- missing/unknown/retry/error 能保留且可审计；
- 128 的结论严格限制在实际覆盖范围；若跨网关条件缺失，明确记 `CONDITIONAL`；
- 报表可以从原始脱敏记录重新生成，统计分母与总量对账。

## Part C：无混杂正式矩阵、功效计划与最终准入

### C.1 目标

在 A 的触发配方和 B 的数据契约冻结后，执行正式对照实验；保证每个条件确实改变目标行为，评估效果、成本、质量和安全，并输出 go/no-go。C 不负责修改 A/B 算法，也不预设优化成功。

### C.2 工作项

1. 冻结 registry 和配置快照：逐臂记录所有相关开关的预期值、生产构造器消费值和断言结果；确认 A 的每项行为变化都在 A 因子内受控，纯观测字段不算行为效果；按 §3.3 主矩阵将 `cache_aware_compaction` 固定，防止 confounding。
2. 先跑无凭证矩阵守卫，确认 Baseline/A-only/B-only/A+B 在配置上独立；再进行小规模 live pilot，证明每臂请求路径、usage 与关键事件能对应到同一匿名样本 ID。
3. 根据 pilot 方差与最小有意义差异做样本量/功效计划；预先冻结统计分析、比较方向、置信区间、停止规则和多重比较处理。每臂 30 个 warm request 且三次运行只是下限，不自动代表有足够功效。
4. 执行正式矩阵。优先用固定任务配对比较并随机化顺序；每个账号/网关/上下文桶在各臂尽量平衡。测试容量不足时可以分期采样，但不得把不同条件的账号/route 暴露差异误认为优化效果。
5. A 因子至少报告两类结果：
   - 受控触发子集的条件效果；
   - 自然任务分布下维护发生率、维护成本和总体影响。
   两者不得合并成一个平均值掩盖触发率。
6. 报告主指标：miss tokens/request、加权 hit rate、总 input tokens/request、summary/projection/rewrite 次数、cold-start 成本、任务完成率、必要信息保留、工具调用正确率、p50/p90 延迟、usage 覆盖率、unknown/error/retry 率及安全事件。
7. 预先定义并执行安全停止：超 hard ceiling、必要上下文丢失、工具调用出现预设严重错误、成员/会话串扰、异常成本或延迟越界时立即停臂、保留证据并回滚。
8. Rescue 仅在受控末端超限场景独立验证；若没有触发，结论是“未验证”，不能以模拟成功替代真实触发证据。
9. 做分层与敏感性分析：账号、网关、model、bucket、cold/warm、触发/未触发；128 的不同归因规则单独报告。任何关键分层样本不足都标 unknown/insufficient，不外推。
10. 依照预注册门槛给出 `GO` / `NO-GO` / `CONTINUE-SAMPLING`；`GO` 只表示可进入单独审批的有限灰度，不自动授权全面发布。

### C.3 写集与协作界面

- 写集：C 专属实验计划、runner、结果和最终分析；不改 A/B 生产实现，不编辑 B 的数据 recorder。需要接口时先和 B 冻结 schema，再由唯一 owner 修改。
- C 负责矩阵和分析，A 负责触发正确性，B 负责数据语义；C 不得为了使结果可读自行改变分母、标签、开关或数据模型。
- C 开始正式运行前须引用 A/B 的接口版本和 PASS/CONDITIONAL 状态，并由协调者批准预算与账号范围。

### C.4 交付与通过条件

C 的交付 `PART_C_NEXT_RESULT.md`：预注册实验契约、pilot/正式样本分流、样本量依据、匿名原始数据位置/hash、所有臂的配置与触发覆盖、分层结果、异常样本表、质量/成本/延迟/安全分析、结论和回滚建议。

C 只有在以下条件全部满足时才可建议进入有限灰度：

- 条件配方真实隔离，A 因子覆盖所有纳入评估的行为变化，目标路径在适当子集中确实触发；
- 样本量满足预注册功效要求，运行间方向和效果不由单一账号/网关支配；
- 预先指定的成本或缓存主指标达到最小有意义改善；
- 质量、必要上下文、工具调用、安全不劣于预设界限；
- 延迟、错误、重试、unknown 与成员隔离满足预设护栏；
- 跨环境结论只限于已测环境，不依赖未经验证的 Provider 常量；
- 默认配置、实际部署开关、灰度范围与可执行回滚完全一致。

任一关键项缺失或统计功效不足，必须建议 `NO-GO / CONTINUE-SAMPLING`。

## 5. 并行节奏、写集隔离与合流

### 第 0 阶段：协调者冻结（短暂前置，不阻塞各侧静态准备）

- 发布固定快照与实验契约模板；裁定默认开关状态、预算、任务与凭证范围；
- 明确条件矩阵、`cache_aware_compaction` 固定值、指标 owner 与禁止修改边界；
- 创建三个隔离工作区和各自报告路径。

### 第 1 阶段：三方并行准备

- A 准备触发配方、安全场景和状态事件映射；
- B 准备观测/质量/延迟数据字典、隐私审查和 128 分析方案；
- C 准备无混杂 registry 守卫、pilot 设计、功效计划模板和成本预算。

各侧先交接口提案，不在共享代码上并发改动。协调者冻结交叉接口后，必要的代码接线由单一 owner 实施。

### 第 2 阶段：统一 pilot 与正式采样

- A 证明触发器与目标行为真实可达；
- B 证明 telemetry 完整、隐私合规、样本能对账；
- C 先跑 pilot 并冻结正式样本量/分析方案；满足前置后再开始正式矩阵。
- A/B 可继续各自只读复核；C 统一调度有凭证的真实 Provider 请求，避免三方重复消耗预算。

### 第 3 阶段：独立复核与决策

- 三方互相交叉审查接口和关键原始样本，但不改写对方结果；
- 协调者在同一个不可变快照重跑 build、test、vet、format、repolint、cache guard 和矩阵守卫；
- 更新总摘要及单独决策记录；明确实际部署默认开关状态、已测范围、未决项和 owner。

## 6. 预算、停止与安全控制

- 真实请求预算必须由协调者事先批准，按 pilot 和正式阶段分别设上限，并为失败/重试预留额度；达到预算即停止，不自动续跑。
- live 实验使用隔离成员与测试任务，限制并发，避免访问或修改用户真实会话；所有会话可追溯到实验 ID，但不暴露用户内容。
- 不把 token 膨胀至 80 万作为唯一触发方式。优先评估隔离实验阈值降低是否安全；若必须构造超大上下文，先计算费用、时延、Provider 限制和数据风险，并经审批。
- 发生超 hard ceiling、跨成员状态污染、严重上下文缺失、工具误操作、异常费用或 latency breach 时立即停止相关臂，保存脱敏证据并回滚。
- 任何生产行为开关如果默认开启，必须在实验前确认目标环境实际状态与回滚路径；NO-GO 不得被误读为开关自然关闭。

## 7. 最终状态与里程碑

### 7.1 本轮完成（可闭环）的标准

- 三个 Agent 的报告、原始脱敏证据、固定快照和协调决策齐全；
- 测试条件与实际消费配置一致，样本与统计结果可复算；
- 质量/延迟数据面可用，账号/route 语义无误；
- 正式矩阵完成，或清楚证明因资源/安全/功效不足而不能完成，并列明续采责任人和条件。

### 7.2 主线优化闭环标准

主线只有在 C.4 全部准入条件满足、协调者批准有限灰度、灰度阶段完成且回滚/质量/成本护栏通过后，才可标记为“优化验证闭环”。仅完成代码审查、触发压力测试、观测改造或本轮矩阵，不等同主线完成。

### 7.3 默认决策

在主线闭环前维持：

> **`NO-GO / CONTINUE-SAMPLING`：不扩大灰度，不宣称缓存收益；完成触发路径、数据质量与有效对照实验后再评审。**
