## 2. B1：预注册假设与判别信号

**诚实声明**：本 Part 在撰写前已做过一轮历史读取（§3），因此下列假设的**登记晚于首次观察**。为减少事后拟合，每条假设同时写入"**什么信号不能证明它**"与"**停止规则**"；§3 的结论只使用 §3 自己列出的判据。

| 假设 | 支持信号（可观察） | **不能**单独作为证明 | 停止规则 |
|---|---|---|---|
| **P1** provider-visible 稳定前缀发生变化 | 同一 member/route 的相邻请求出现 prefix hash 或 reason 变化；且变化后的 miss 有可重复增量 | `stable_prefix_changed=true` 本身——它只说明本地 hash 变了，不证明 provider 因此 miss | 若一次会话内 prefix hash 全程不变而 miss 仍高 → P1 排除，转 P3 |
| **P2** 请求新增内容/工具结果变大 | 固定前缀下 prompt/miss 同步增长，且增量与本轮新增内容/工具输出的 token 量相符 | 单纯 `stable_prefix_changed=false` 不能证明其余内容没变 | 若 miss **显著大于**本轮新增内容 → P2 不足以解释，转 P1/P3 |
| **P3** 请求间隔、缓存生命周期或缓存作用域 | 固定任务/前缀下命中随间隔或 TTL 条件呈**可重复**变化；或 route/账号池变化导致同 hash 不同 hit | 把 `hit == 0` 直接称为冷启动；把一次间隔差异当作 TTL 证据 | 若各间隔分层的命中率**没有阶跃** → 简单 TTL 不成立（不等于 provider 无缓存作用域问题） |
| **P4** usage 口径或聚合造成表观变化 | 异常集中于特定 usage source、聚合 attempt、缺失/估算，或某种字段约定 | `prompt == hit + miss` 单项闭合检查（本地写入时即被改写，见 §4） | 若排除聚合/未知样本后跌幅不变 → P4 不足以解释 |
| **P5** 模型/route/任务组成变化 | 变化集中于特定 model/route/member/工作负载；**分层后总体差异明显减弱或消失** | 不分层的总体日均命中率 | 若同桶内（同尺寸、同 model）跌幅仍在 → P5 排除 |

**本轮新增的两条派生假设**（由 §3 的观察提出，须由 §5 的实验判定）：

| 派生假设 | 内容 | 判别信号 |
|---|---|---|
| **D1（前缀中段被每轮重写）** | 同一会话内，前一次 prompt 的固定比例（约 20–40%）每轮都重新计为 miss；损失与 prompt 成比例而非固定 token 数 | 相邻请求的 **首个分歧字节偏移** 落在 prompt 内部且按比例移动；客户端 hash 流显示 prefix 变化 |
| **D2（provider 侧缓存作用域/容量变化）** | 客户端字节完全稳定，但 provider 只为前缀的一部分提供服务（容量、scope、账号池或网关行为变化） | 同一字节序列在**同 route 短间隔**下命中率**下降**；对照组（不同 route、同客户端）不受影响 |

**止损与样本量**（M2 门槛，先于正式实验确定）：

- 每个条件先做 **pilot ≥ 8 个请求**估计波动；正式实验每条件 ≥ 20 个 warm 请求才报加权率，否则只报 `insufficient_sample`。
- 单变量原则：一次只改一个因素，禁止同时切换模型、route、任务与缓存相关配置。
- 若 pilot 显示同日同条件的请求间命中率极差 > 15pp，先把样本量翻倍再谈因果。

### 3.4 P2 —— 内容增长

在"同会话、append-only"的紧邻对上（间隔 ≤5s、增长 <5%），本轮新增内容（即 prompt 增量）与 miss 分开测量：

| | 09-23 | 09-24 |
|---|---|---|
| 每轮新增内容 p50 | **1,178** tokens | ~1,845 tokens |

miss 比本轮新增内容**大一个量级**，且新增内容本身两天基本相同。**P2 判定：不能解释跌幅**（内容是背景量，不是变化量）。

### 3.5 P1 —— 前缀变化（唯一与数据相容的客户端侧解释）

用**严格链**（≥4 条连续行、每条间隔 ≤30s、每条增长 <15%）进一步排除"相邻行属于不同并发会话"的混淆——这是路由级账本最大的陷阱：

| 日期 | 严格链数 | 转移数 | 上次 prompt 的未命中 p10 / p50 / p90 | 最大并发（行/60s） |
|---|---:|---:|---|---:|
| 09-22 | 66 | 337 | 0.2% / **5.8%** / 11.4% | 61 |
| 09-23 | 123 | 674 | 0.2% / **6.8%** / 16.1% | 24 |
| 09-24 | 122 | 986 | **21.4%** / **33.6%** / 44.3% | 17 |

三点值得强调：

1. 09-24 的 **p10 已是 21.4%**——九成同会话相邻请求至少重付 21% 的旧前缀；健康日的 p10 是 0.2%。
2. 09-24 的**并发反而最低**（17 行/60s vs 61/24），所以"并发交错造成的假象"**不能**解释它；若按交错解释，09-22 应最差。
3. 未命中量对 prompt 的回归斜率约 **0.28**（corr 0.69），而对"最近 5/10/20 轮增量"的斜率仅 ~0.09（corr ~0.25）。即**损失与 prompt 成比例**，不是固定尾巴——这正是 `MEMBER_CACHE_TAIL_ROUTE.md` 里"固定尾巴 4000–7500 token"模型**不再成立**的地方。

### 3.8 对 `TEAM_MEMBER_CACHE_HITRATE_ANALYSIS.md` §7（H1）的证伪

1. 实测每轮新增内容 p50 仅 **1,178–1,845** tokens，而该桶均值 miss 为 8,702 ⇒ 代理值比真实新增内容**高 4–7 倍**，"不可避免"部分被高估。
2. 大上下文两桶（`256k_512k`/`512k_768k`）的均值 miss 里，**41.7% / 47.1% 来自 `hit == 0` 的冷行**（`512k_768k` 桶 32 行中 5 行为冷请求，贡献 3,145,512 miss）。把冷行混入"每轮可回收"会显著夸大结论。
3. 剔除冷行后的 warm 均值 miss 为 65,252 / 131,071，对应复用率 83.8% / 88.5%——**大上下文在健康日并不低命中**（并与 §3.6 的 98.9%@280K 一致）。

**结论：§7 的 +5.07pp 估计不成立，应在 Part A 的报表里作废或重算。**

## 4. 为什么 §3 无法把 P1 与 D2 分开（code anchor）

`internal/provider/anthropic/messages_usage.go` 的 `messagesUsage` 决定账本里的 `hit`/`miss`：

```go
miss := inTok + cacheCreate
prompt := inTok + cacheCreate + cacheRead
if inclusive {              // c.deepseek 为真（DeepSeek 的 Anthropic 兼容路由）
    miss = max(inTok-cacheRead, 0)
    prompt = cacheRead + miss
}
```

- `prompt == hit + miss` 是**本地构造**的，因此 NEXT_STEPS §1 把"闭合检查"列为不可单独作证的信号是对的。
- 该路由的整个口径由**一个布尔**（`internal/provider/anthropic/anthropic.go:258` `inclusiveInput()`）决定。若上游改变了 `input_tokens` 的含义而该布尔未变，**报告的 split 会整体位移而真实缓存行为不变**——这属于 P4，而账本**不存原始字段**，无法判定。
- 这直接说明：**要分开 P1 与 D2，必须有逐请求的原始 usage 与前缀身份**，即 Part A 已落地的 `.cache_requests.jsonl`（§10.2 判据）或 §5 的对拍实验。**历史账本对此已到极限。**

## 5. B2.2：可复现实验设计

### 5.1 实验 A（客户端字节，离线、零成本、可复现）

**目的**：判定 P1——今天这次构建在**成员形状**的长会话里，provider-visible 前缀是否逐轮逐字节稳定。

- 驱动真实 agent 栈（真实 system 前缀 + 成员 provider-visible 工具面 + append-only 会话），provider 端用**前缀缓存模型**：`hit = 与上一次请求的逐字节公共前缀`。
- 记录每请求：`prompt tokens`、`hit`、`miss`、**与上一请求的首个分歧字节偏移**、复用率。
- 单变量：上下文规模阶梯（短/中/长）；对照组 = 加大工具面（模拟"未延期"的表面）。
- 判据：若首分歧偏移总在**尾部新增处**、复用率 ≈ `1 - 新增/prompt`，则 P1 在客户端侧被**证伪**，§3 的现象必须归给 D2；若偏移落在 prompt 内部，则 P1 成立并可定位到具体字节。

### 5.2 实验 B（provider 作用域，需真实 provider）

**目的**：判定 D2，并给 §3 的现象定性。

- 固定 member、route、模型、任务脚本；同一字节序列做**短间隔重复**（2s 内）与**长间隔恢复**（超过疑似 TTL）；再与**另一条 route** 同字节对拍。
- 关键对照：**同一 route 的昨日与今日**（09-23 与 09-24 的同形状请求）——若字节一致而命中率不同，D2 成立。
- provider 未返回 cache split 或返回不完整时标 `unknown/not applicable`，不参与判定。

### 5.3 实验 C（版本对拍，判定 §3.7 的邻接提交）

在同一台机上，分别用 `e17c7eae1` 之前/之后的构建跑**同一固定脚本**（同 member、同 route、同 prompt），比较逐请求复用率。这是唯一能把"时间相邻"变成"因果或排除"的做法；**不做这一步就不得回滚该提交**。

### 5.4 交付与判定（B3 门槛）

只有同时满足下列条件，才实现行为改动（否则合格交付是"**不应实施**"并附负结果）：

1. 主指标改善超过 pilot 波动，且跨重复运行方向一致；同时报绝对 pp 与 miss tokens/request。
2. 任务成功率/质量不劣于预设容忍范围；长上下文不得以遗漏必要上下文换命中率。
3. 延迟、总输入 token、成本、工具调用次数无不可接受回退。
4. 改动前后 route、模型、样本筛选、usage source 与统计口径一致，排除项全部公开。
5. 改动必须有开关或可快速回滚，并按 Team/member 白名单灰度。

### 9.2 四条结论

1. **P1 在客户端侧被证伪（就这些形状而言）。** 除折叠后那一次外，**每一次请求都复用了上一次请求整个消息数组**（`appended == 0`），包括每轮换一份新 workspace/background-memory 快照的臂。会话上下文的更新是**追加新消息**，不是在原位替换——`session_context` 不重写已发送字节。测试断言 `appended >= 0`（折叠后一次除外），因此这是一个可长期持有的回归守卫。

2. **折叠的代价是"一次、可量化、且只影响内容不影响前缀"**：折叠后第一次请求复用率掉到 ~1.4%（这是预期冷轮），随后立刻回到 100%；全程 **stable prefix（system + tools）hash 一次未变**；折叠次数 4、重写次数 4，即**每次折叠恰好一次重写**。

3. **工具块就是那个"固定尾巴"，其与命中率的关系被精确复现**：整体复用率 ≈ `1 - 工具块/prompt`。短臂 ~14K 字符 → ~70%；长臂 ~119K 字符 → ~95%。这与 `MEMBER_CACHE_TAIL_ROUTE.md` 的模型一致，也解释了同样的尾巴为何在小上下文上严重、在大上下文上几乎消失。延期工具在本夹具里把工具块从 6,526 降到 4,127 字符（-37%）。**注意本夹具只注册 4 个常驻 builtin，不是真实成员表面**；真实足迹以 `internal/boot/member_surface_tokens_test.go` 为准（成员 1,567 vs leader 3,397 tokens）。两者方法一致、数值不同，不要混用。

4. **工具输出体积只改变内容量，不改变前缀稳定性**：`large-tool-output` 臂把每轮新增从 ~2K 推到 ~15K 字符（复用率随之从 ~85% 降到 ~28%），但 `appended` 仍恒为 0。这**定量支持** §3.4 的判断——P2 是背景量（影响绝对 miss），不是跌幅的**变化**来源。

### 9.3 这个臂**没有**解释生产上的跌幅

生产账本里 09-24 的单请求未命中是 **~30K tokens**（§3.4），而本夹具的工具块只有 ~1–1.6K tokens、折叠后冷轮也只是把当次复用率压到 ~1.4%。也就是说：**"客户端重写前缀"与"工具块尾巴"这两条已量化的路径，都不足以解释生产跌幅**。剩下的解释只有两类，都必须由 §5.2/§5.3 的真实实验判定：

- 本臂**未覆盖**的形状：原生 tool-search 的延期 MCP 尾巴、图片附件、或某条 host 路径在请求构造中重排消息。
- **D2（provider 侧作用域/容量）**：客户端字节稳定而 provider 只为前缀的一部分提供服务。
