## 1. A1 数据质量与统计单位

### 1.1 字段数据流表

原始 provider 计数器 → 归一化 → 落盘，三段各不相同，混用即错：

| 层 | 位置 | 字段 | 语义 |
|---|---|---|---|
| 上游 wire | DeepSeek 网关 `/v1/messages` | `input_tokens`、`cache_read_input_tokens`、`cache_creation_input_tokens` | 口径**不携带判别位**：inclusive 与 exclusive 的同一字段名含义相反 |
| 适配归一化 | `internal/provider/anthropic/messages_usage.go` | `messagesUsage(inTok, outTok, cacheCreate, cacheRead, billedWrite, inclusive)` | 按路由声明的口径折算出 `PromptTokens` / `CacheHitTokens` / `CacheMissTokens` / `CacheWriteTokens`；`inclusive` 由 `client.inclusiveInput()`（= 该 client 是否 `deepseek`）决定 |
| 采样合并 | `internal/agent/run_usage.go` `mergeSamplingUsage` / `finalizeSamplingUsage` | 同上 + `RequestCount`、`Context*` | 多 attempt 累加；`PromptTokens` 被重写为 `hit+miss`；`ContextPromptTokens` 只取最后一次 attempt |
| 账本落盘 | `internal/stats/recorder.go` → `record` | `prompt`、`cache_hit`、`cache_miss`、`completion`、`requests`、`model`、`ts` | 即归一化后的值；**不含**原始 wire 字段、不含 team/member、不含前缀诊断 |

**三处必须记住的等式与不等式**：

1. `prompt == cache_hit + cache_miss` —— **构造不变式**。适配层两种口径都保证它（`messages_usage.go` 注释与 `TestUsageEveryConventionKeepsTheBillingInvariant` 都明说），`finalizeSamplingUsage` 还会把 `PromptTokens` 重写成 `hit+miss`（`run_usage.go:237`）。因此**该等式成立不构成对上游口径的任何验证**。
2. `prompt != 请求的实际 prompt`（多 attempt 聚合时）。仅当 `requests == 1` 时，归一化后的 `prompt` 才等于该请求自身的 prompt 形状。
3. `cache_write` 是 miss 的**子集**，不是加数。

### 1.2 旧账本可验证 / 不可验证清单

| 事项 | 可否用本机账本验证 | 依据 |
|---|---|---|
| 账本行内部自洽（`prompt == hit+miss`） | ✅ 可验证 | 三天全部成立 |
| 上游是 inclusive 还是 exclusive | ❌ **不可验证** | 适配层归一化后原始字段即丢弃；账本不保留 `input_tokens`/`cache_read_*` |
| 上游是否发生重复计数 | ⚠️ 只能启发式判别 | 见下方判别式；是启发式，不是独立核对 |
| 分成员归属 | ❌ 不可验证 | 账本无 team/member 维度 |
| 冷启动 / 前缀变化 / fold | ❌ 不可验证 | 无 session 身份、无 `stable_prefix_hash`、无 `prefix_change_reasons` |
| 多 request 聚合的拆分 | ❌ 不可拆分 | `requests > 1` 只有合计值，无法还原为逐 attempt |

**唯一可用的口径判别式**（§1.4 的 `double-count shape` 计数）：若上游为 inclusive 而被当作 exclusive，则 `0 < prompt − 2×cache_hit < 500`。三天实测该形态的行数为 **1 / 3 / 3**（占 0.1–0.2%），且 `prompt − 2×cache_hit` 的中位数为大负数（−31K…−55K）。**结论：账本与"inclusive 被正确声明"一致**，但这是启发式，不等于核对了上游。

### 1.3 有效样本规则（主基线）

主基线只收：`requests == 1`（单 provider request）且 `accounting_valid`（`hit+miss == prompt` 且非负）且 `hit+miss > 0`（有 cache split）且 `ts` 可解析。

以下各自独立计数、**不静默并入、不修正**：`requests > 1` 聚合、无 cache split、未知/估算、账目无效、时间戳不可解析、窗口外、非成员范围。聚合行的 token 在报表的 `exclusions.aggregate_hit_tokens` / `aggregate_miss_tokens` 单独入账，因此"全样本率"可显式加回，而不是发现总数悄悄少了一块。

## 2. A2 同口径基线

### 2.1 时间与样本

- 账本三天：09-22 本地 19:27–23:59（**仅晚间**）、09-23 全天、09-24 00:00–**07:15**（此后无任何流量，Team 未运行）。
- **整天对整天不可比**：09-24 只是部分日。同时段（00:00–07:11）比较同样不可比——09-23 在该时段只有 174 条且止于 01:34，09-22 该时段**没有流量**。
- 因此本文采用**等样本量**比较：各取窗口内最早的 1,714 条行（`--first 1714`），这是三天中唯一样本量可对齐的口径。

### 2.2 等样本量双臂

| 指标 | 09-23 臂 | 09-24 臂 | 变化 |
|---|---:|---:|---:|
| 单请求样本数（计入基线） | 1,647 | 1,656 | — |
| token 加权命中率 | **85.1%** | **68.4%** | **−16.7pp** |
| 请求率 p10 / p50 / p90 | 83.9 / 90.8 / 95.2% | 53.6 / 68.5 / 80.9% | 整体下移 |
| 均值 prompt | 88,713 | 92,879 | +4.7% |
| hit / miss tokens | 124,347,648 / 21,762,148 | 105,157,632 / 48,649,797 | miss ×2.24 |
| 排除（聚合 / 无 split） | 58 / 9 | 57 / 1 | 相当 |

排除聚合样本后仍需注意：这仍是**路由级**样本，不是成员级（§4.2）。

### 2.3 分布形状

p10/p50/p90 三个分位同时大幅下移，说明不是尾部或个别请求恶化，而是**整个请求群体的命中水平一起下移**。这与"某些请求整段前缀失效"不同——后者的近全 miss（<10%）行数应当上升。在两条等样本臂的单请求行上实测：09-23 有 21 行（1.3%）近全 miss、承载该臂 miss 的 27.3%；09-24 只有 2 行（0.1%）、承载 0.3%。**09-24 的近全 miss 反而更少**，而总 miss 是 09-23 的 2.24 倍——所以多出来的 miss 不是少数请求整段失效，而是多数请求各多丢一块。

### 2.4 分桶：排除"prompt 变大"这一解释

| 桶 | 09-23 n / 均值 prompt / miss·每请求 / 命中 | 09-24 n / 均值 prompt / miss·每请求 / 命中 |
|---|---|---|
| `<32k` | 83 / 29,161 / 6,876 / 76.4% | 13 / 30,307 / 14,996 / 50.5% |
| `32k_128k` | 1,393 / 71,070 / 7,015 / 90.1% | 1,428 / 84,252 / **27,869** / 66.9% |
| `128k_256k` | 116 / 159,768 / 23,528 / 85.3% | 215 / **153,960** / **40,268** / 73.8% |
| `256k_512k` | 25 / 335,539 / 89,165 / 73.4% | — |
| `512k_768k` | 30 / 592,242 / 215,363 / 63.6% | — |

两处关键读数：

- `32k_128k`：均值 prompt 只涨 18.5%，每请求 miss 涨 **297%**。
- `128k_256k`：均值 prompt **更小**（−3.6%），每请求 miss 仍涨 **71%**。

⇒ **"prompt 变大导致命中率下降"在 09-24 的分桶里被自己的数据排除。**

### 2.5 偏差与不平衡（必须与数字同读）

- 09-22 只有晚间流量（19:27 起），09-23 全天，09-24 只有凌晨到早间。三天的**任务组成未知且很可能不同**，等样本量只对齐了样本数，没有对齐工作负载。
- 成员级归属不可得（§1.2）。四个 ipc-* 成员与任何其他使用该路由的会话混在一起。
- provider 侧状态（TTL、并发、缓存逐出）不可观测，是未控制的混杂因素。
- `mean_prompt` 在两臂相差 4.7%，但桶内分布（尤其 ≥256K 只有 25/30 条）样本很小，桶级结论置信度低。

## 3. 长上下文可回收量（**假设，最需要被攻击的一段**）

**H1**：`32k_128k` 桶的每请求 miss（09-23 臂 = 7,015 tokens）可作为"每轮不可避免新增内容"的代理。该桶 1,393 条、命中 90.1%，其 miss 主要由当轮追加的新内容构成。

**H1 的替代解释**：大上下文的当轮新增内容本身可能远大于 7,015（例如整文件读取、长工具结果）。若如此，本节结论大幅缩小甚至归零。**账本无法区分这两种解释**（无前缀诊断，§1.2）。

在 H1 下（09-23 等样本臂）：

| 桶 | n | miss/每请求 | 命中 | 可回收 | 占该桶 miss |
|---|---:|---:|---:|---:|---:|
| `256k_512k` | 25 | 89,165 | 73.4% | 2,053,734 | 92.1% |
| `512k_768k` | 30 | 215,363 | 63.6% | 6,250,446 | 96.7% |
| 合计 | 55 | — | — | **8,304,179** | — |

- 占该臂 miss 的 **38.2%**
- 臂内加权率：**85.11% → 90.79%（+5.68pp）**
- 稳健性：改用臂内整体均值 miss/每请求（13,213）作代理，为 **+5.45pp**。⇒ 对代理选择不敏感。

**这与"长上下文"的关系**：大上下文的每请求 miss 比小上下文高 **13–31 倍**；在 H1 下其中 92–97% 是可回收的。**可提升的空间几乎全部集中在长上下文**，而若 H1 不成立，这些 miss 是真实内容增长，属内容治理（限制工具输出体积、分段读取），缓存机制无法解决。

### 4.3 本次真实会话给出的两个新证据

1. **成员的共享 provider-visible 前缀 = 2,816 tokens**（system + 工具 + 身份 + 技能，经真实构建器测得），且它**跨请求稳定命中**。三个成员的首请求都命中同一 2,816 tokens，miss 恰好等于各自独有的首条消息（0 / 30,994 / 153,214）。
2. **追加内容很小时的 warm 请求 miss = 0**（9 条 warm 请求，miss 全为 0）。

这两点合起来对 §3 的 H1 是一个**不利**证据：如果生产环境每请求 miss 达到 7,015–215,363 tokens，而**固定部分（schema+身份+技能）只有 2,816 tokens 且已被缓存**，那么生产的 miss 更可能来自"当轮追加的内容"（P2）而不是"固定尾巴"或"被破坏的前缀"。**H1 仍然未证明，但它的替代解释现在有了正面证据。**

### 4.4 本轮修复的一个归因缺陷

真实会话暴露：当一层的低命中**只**来自它的首请求、而 warm 样本 miss 为 0 时，我仍会给出 `stable_prefix_high_miss_unattributed`（证据行写着 "median miss 0 tok"）——**没有 miss 却声称尾部问题**。已修为"固定前缀样本的总 miss 为 0 时不作任何尾部结论"，并由 `TestDiagnosisDoesNotClaimATailWithNoMiss` 固定。`128k_256k` 桶现在只给 `insufficient_sample`，这是诚实的。

## 6. 对前置分析的两处更正

1. **`prompt == hit + miss` 的闭合检查是循环论证。** 前置分析 §4.1 用它作为"排除重复计数"的证据之一。实际上该等式由适配层保证（§1.1），因此**不构成证据**。可用的只有 `prompt − 2×hit` 的启发式判别（§1.2），且它也只是启发式。结论（未发现重复计数）不变，但**证据等级下调**。
2. **满日对部分日的比较不成立。** 前置分析用 09-23 全天 83.8% 对 09-24 部分日 67.7%。本文改为等样本量比较（85.1% vs 68.4%），幅度略大（−16.7pp vs −16.1pp），结论方向一致但口径已修正。

两处的共同教训与前置分析 §11 相同：**从单一视角的有限证据推断全量**——第一次是"闭合即无重复计数"，第二次是"两天可以直接比"。
